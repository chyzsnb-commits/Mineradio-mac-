# AI 分轨热管理与实时去人声增强设计

## 目标

在不增加界面按钮、不影响升降 Key 和 AI 双轨播放的前提下，降低本地 AI 分轨对播放流畅度、温度和电池的影响，同时改善实时模式伴奏轨中原唱残留明显的问题。

## AI 热管理

- AI 任务开始时读取一次当前电源与温度状态；任务运行中拔电或升温不强制中断，下一次任务再采用新档位。
- Apple Silicon、内存不少于 12GB、插电且温度为 `nominal` 时使用 `batch 2`。
- 电池供电、Intel Mac、低内存或温度为 `fair`、`serious`、`critical`、`unknown` 时使用 `batch 1`。
- macOS 使用 `nice` 以较低调度优先级启动 AI 子进程，减少与播放器和界面争抢 CPU。环境变量只作为底层库兼容提示，不宣称能完整限制 CoreML 或 ONNX Runtime 线程。
- 处理状态记录本次使用的 `batch`、电源和温度，便于日志排查；不增加新的常驻轮询。

## 实时双掩码

- 仍只执行一套左右声道 FFT，不增加第二个 Worklet，不增加音频线程内存分配。
- 伴奏估计使用更强的中置消除掩码，优先降低原唱残留。
- 人声估计继续使用现有的相位、瞬态和高频保护，减少鼓点泄漏。
- 输出按现有两个滑块混合：`伴奏音量 * 伴奏估计 + 人声音量 * 人声估计`。
- 两个滑块均为 100% 时继续走原声旁路，升降 Key 位于最终混音之后，行为不变。

## 验证

- 单元测试覆盖电池、插电、温度、芯片和内存对应的 batch 选择。
- 单元测试确认 macOS AI 命令使用低优先级启动，其他平台不套用 `nice`。
- 合成音频测试分别约束伴奏轨的人声残留、人声轨的鼓点泄漏和人声保留比例。
- 静态测试确认实时处理仍只有一套 FFT 且帧内零分配。
- 运行 `npm run check`，再用独立用户目录启动 Electron 做基本启动检查。

## 不在本次范围

- 不更换 UVR 模型，不实现新的流式 AI 模型。
- 不在正在处理的任务中途动态切换 batch。
- 不承诺 `batch 1` 一定降低总耗电；它主要降低峰值压力，实际耗电仍需真机长期测试。
